# Injury Data Visibility

Decision (owner, 2026-11-21): the platform does **not** surface injury information to
parents. `firestore.rules` can never do that, and the fix is a migration. This file
records what is exposed, why rules cannot close it, and what the migration costs.

## What is exposed today

`teams/{teamId}/roster/{entryId}` carries a denormalised injury summary:

```
injuryStatus, injuryNote, injuryBodyPart,
injuryUpdatedBy, injuryUpdatedByName, injuryUpdatedAt,
injuryClearedBy, injuryClearedByName, injuryClearedAt, injuryReportId
```

The roster read rule:

```
allow read: if signedIn() && (
  isAd() || isTeamMember(teamId)
  || (memberRole(teamId) == 'follower' && request.auth.uid in resource.data.guardianUserIds)
);
```

and `isTeamMember(t)` is `memberRole(t) in ['coach','staff','player','parent']`.

So three groups read the whole entry, injury fields included:

| Caller | Sees injuries of |
|---|---|
| Any **player** on the team (`isTeamMember`) | **every teammate** |
| Any **parent** holding a `parent` membership | **every athlete on the team** |
| Guardian via `guardianUserIds` | their own athlete (fine) |

The player case is the real exposure: a teammate can read another child's body part,
note and clearance. Parent memberships are usually `follower` (acceptInvitation maps
them), so that row is rarer but real wherever a membership was created with role
`parent`.

## Why rules cannot fix this

Firestore security rules are **document-level**. There is no field-level read
permission. If a caller may read the roster document — and players must, to see
teammates' names, numbers and positions — they read every field on it.

Narrowing roster read instead would break legitimate features:

- a player's own team roster view;
- the statistician flow, where a parent or player scores a game and needs the roster;
- `isGameScorer` paths that resolve roster entries.

So the acceptable fix is to remove the data, not to remove the read.

## The migration (not done)

`injuryReports` is already the authoritative, staff-only record
(`isCoachOf || isStaffOf`), and it holds *more* than the summary: status, bodyPart,
severity, description, expectedReturn, reportedBy/At, clearedBy/At, cleared boolean.
Verified on the live fixture: three historical reports, all fields present.

Plan:

1. **Confirm iOS does not need the summary.** `RosterEntry` decodes the ten fields
   directly; the roster list shows an injury badge. Removing them means the badge
   disappears unless iOS is changed to read `injuryReports` (staff-only, so coaches
   still see it; players correctly would not).
2. **Back up** the eleven teams' roster documents before touching them.
3. **Strip the ten `injury*` fields** from roster documents. Field deletion, not
   document deletion — names, numbers and positions are untouched.
4. **Update iOS**: coach roster view reads the latest `injuryReports` entry per athlete;
   player and parent views show nothing.
5. **Verify**: a player token reads a teammate entry and finds no injury field; a coach
   token still sees clearance status.

Rollback: the summary is derivable from `injuryReports`, so it can be regenerated by
script. Nothing unique is lost.

## Interim state (current)

- **Writes**: guardians cannot write any injury field (whitelist excludes them);
  players cannot write the roster at all (`allow write: if canManageTeam`). Verified.
- **Reads**: unchanged. The exposure above stands until the migration runs.
